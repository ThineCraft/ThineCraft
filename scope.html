ThineCraft ecosystem scope

ThineCraft

Status: Ecosystem in formation. This document describes intended direction; it does not claim that working product implementations exist.

Project website

Purpose

ThineCraft is the planned family of open tools for creating, collaborating, and retaining ownership of organizational knowledge. The core premise is that cloud convenience should not require permanent dependence on one vendor.

Confirmed principles

  • Organizations should be able to understand, host, move, export, and retain a usable copy of their work.
  • Open formats, portable services, inspectable behavior, and organization-controlled infrastructure are preferred.
  • Projects should operate as a connected family without collapsing into one monolithic application.
  • Hosted convenience, self-hosting, and hybrid continuity should preserve the meaning of the data.
  • Planned capabilities must remain clearly distinguished from implemented and verified behavior.

Current core project set

  • ShareCraft: SharePoint-style sites, knowledge, document libraries, lists, governance, and collaboration.
  • DriveCraft: cross-platform sync, metadata, migration, and organization-controlled offline continuity.
  • TeamCraft: portable team communication, meetings, decisions, and context.
  • GanttCraft: understandable project schedules, dependencies, resources, and change.
  • FlowCraft: inspectable workflows, connectors, execution evidence, and recovery.
  • ShowCraft: diagrams, animation, business intelligence, and digital twins.
  • FormCraft: browser, PDF, paper, guided capture, and verifiable form records.
  • ThineCraft: shared direction, ecosystem discovery, and cross-project decisions.

Related applications and services

  • WordCraft, GridCraft, PdfCraft, SolidCraft, and DeckCraft are expected co-authoring or content-creation applications.
  • ThineWedding, ThineMemorial, and ThineCapture are services built on ShareCraft; they are not part of the current eight core repositories.
  • TradeCraft is deliberately excluded until its purpose is defined.

Boundaries and non-goals

  • Public placeholder repositories and websites do not imply working implementations or production readiness.
  • The ecosystem should share contracts and context without forcing every project into one deployment or codebase.
  • External interoperability must not quietly become permanent vendor dependence.
  • Future open-source licensing is intended, but licenses and contribution governance remain to be selected explicitly.

Cross-project open decisions

  • Shared identity, tenancy, permissions, policy, audit, and governance.
  • Canonical object identifiers, metadata, events, search, links, and synchronization contracts.
  • Hosted, self-hosted, hybrid, offline, and disaster-recovery reference architecture.
  • Licensing, contribution model, project governance, security policy, and release maturity labels.
  • Common design system, accessibility baseline, localization, observability, and documentation standards.

Guidance for AI contributors

  1. Read the target repository's scope.html before proposing architecture or features.
  2. Treat confirmed direction, boundaries, and open decisions as different categories.
  3. Do not convert an open decision into a fact without an explicit project decision.
  4. Never imply that placeholder capabilities are implemented, tested, released, or production-ready.
  5. Preserve portability, open formats, inspectability, self-hosting, and organization-controlled continuity.
  6. Update the relevant scope.html whenever a product decision changes project scope.
